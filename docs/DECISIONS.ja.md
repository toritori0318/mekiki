# 設計判断の記録

規約と lint の主要な採用・不採用の判断。

運用方針: **規則は実コーパス（6プラグイン・約190スキル）で測ってから出し、
働かない規則は採用しない。** 大半のスキルに出る警告は無視されるだけで、1件も捕まえない規則は
コストだけを生む。どちらも実際に起きており、以下に記録している。

English: **[DECISIONS.md](DECISIONS.md)**

**数値について:** 以下の各判断が引く実測件数（154〜192スキル等、文書によって異なる）は、
コーパスが育つ過程の異なる時点で取ったスナップショットであり、開発期間を通じて単調に
増えている。値を揃えていないのは測定のブレではなく、その判断を下した時点でのコーパス
サイズをそのまま記録しているため。

## 採用したもの

1. **コンテキスト最小性の検問（既知・削除・行動・層・重複）** — 無関係情報は精度を直接下げる。
   根拠: Chroma "Context Rot"（distractor 1件で劣化。 https://research.trychroma.com/context-rot ）、
   GSM-IC（ https://arxiv.org/abs/2302.00093 ）、Lost in the Middle（ https://arxiv.org/abs/2307.03172 ）、
   Anthropic "the smallest possible set of high-signal tokens"
   （ https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ）
2. **サイズ規律は行数＋推定トークンの2本立て（L19）** — 公式目安 "under 500 lines and 5,000 tokens"。
   日本語は1行平均約76字で行数だけでは空振りする（実測: 500行超1件に対し5,000字超93件）。
   CJK は1字=1.2トークンで概算（新世代トークナイザで CJK 15〜35%増の計測報告）
3. **eval は公式2形式（`evals/evals.json`＋`evals/eval_queries.json`）** — 独自形式は発明しない。
   初期に独自スキーマを定義していたが、公式準拠のスキルを「非標準」と誤検知したため撤回。
   https://agentskills.io/skill-creation/evaluating-skills /
   https://agentskills.io/skill-creation/optimizing-descriptions
4. **測定方法論** — with/without の2回実行と delta（pass率・時間・トークン）、発火精度は
   約20クエリ×各3回・train/validation 60/40 分割。runner は skill-creator に委譲し自作しない
5. **副作用スキルの `disable-model-invocation: true`（L20）** — requires と違いランタイムが
   実際に解釈する唯一の発火抑止機構。機械検証は課金スコープのみ（他リスクの検出語は実測68%に
   当たり行動可能でないため規約要求に留める）
6. **組織固有値・検出語の config 外出し** — ガードスキル名（L8/L20）と検出語（L2/L3/L6/L8/L11）は
   `config.json` で上書き。コードに固定すると他組織・他言語で lint が壊れるか無効になる
7. **命名の機械強制は公式制約のみ（L1）** — 種別3分類の強制は実測で「指摘の全件が公式的に有効な名前・
   catch-all で6割が素通り・真の問題（ディレクトリ名不一致）は0件」だったため [SHOULD] に降格
8. **when_to_use は公式キーとして扱う（L2/L12）** — description に連結され合算1,536字まで
   スキル一覧に載る（ https://code.claude.com/docs/en/skills#frontmatter-reference ）。
   かつて非標準扱いだった L12 警告は全件が誤検知と判明し撤回
9. **スキル新設ラダー・Delta モード・成果物の IR 化・簡略化マーカー・atomic deliver** —
   archify（ https://github.com/tt-a1i/archify ）と ponytail
   （ https://github.com/DietrichGebert/ponytail ）から移植。詳細は規約の各節
10. **成熟度 Tier（0〜3）** — 独自尺度（公式標準に成熟度モデルは無い）。SLSA の累積保証レベルと
    同型（ https://slsa.dev/spec/v1.0/levels ）。単一ラダーが別軸の進捗を隠す問題には
    「Tier=総合値、軸別=viz バッジ」の二層で答える。第三者スキルの供給網トラスト
    （Snyk ToxicSkills: https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/ ）は
    スコープ外と明示

11. **Go・単一バイナリ・サブコマンド** — CLI の採用障壁は配布だった。検証は190スキルの
    実コーパスに対する差分テストで行い、判定器には mekiki 自身の diff モードを使った。
    error は完全一致し、残った差分は厳密に改善のみ（旧実装が `.py`/`.sh` しか見ておらず
    見逃していた実欠陥6件、旧実装が出していた誤検知2件）。

12. **安全規則は recall 優先、品質ヒューリスティックは precision 優先** — 上記の実測で
    見つかった非対称性。`risk_*` は error severity を出すため取りこぼしが誤検知より悪く、
    語境界はむしろ害になる（Go の RE2 は `_` を語構成文字とみなすため `\bbrowser\b` が
    `09_browser-operation-notes.md` にマッチしない）。一方 `deterministic` は人が
    トリアージする warn を出すため両側に境界を付ける（境界なしの "ratio" は
    generation・iteration・migration にも当たり誤検知61件、"comput" は計算ではなく
    ツール名の "computer.type" に当たった）。

13. **参照整合性はリンクだけを見る（L22）** — 当初は「本文に現れるパス様の文字列はすべて
    実在すべき」という規則だった。154スキルの実コーパスで測ると **53件の指摘が出て、
    そのうち欠陥はゼロ**。スキル本文を支配するのは、スキル作成ガイドの例示
    （「**Examples**: `references/finance.md` for financial schemas」）と、他スキルの
    ファイルへの散文的な言及（「querying-warehouse の
    references/04_RECONCILIATION_GATES.md を参照」）で、どちらも「そのファイルがここにある」
    という主張ではない。規約4ディレクトリ配下の Markdown リンクに限定するとこの層が
    まるごと消える（`<link>` プレースホルダや `${CLAUDE_SKILL_DIR}/...` 変数も範囲外に
    なる）。絞り込んだ規則は同じコーパスで **1,381件のリンクを対象にし、破損ゼロ**。
    これは「検査対象が無い規則」とは別物で、健全な母数を持つ規則が今は通っている状態。

14. **`requires` / `depends_on` の参照切れ（L21）は実測なしで採用** — 測定に使えた
    コーパスにはこれらの宣言が **1件も存在せず**、規則を働かせられなかった。それでも採用
    した理由は、却下した `name` 追加検査との違いにある。あちらは検査対象（name）が全
    スキルに存在するのに一件も違反が無かったのに対し、こちらは検査対象そのものが不在。
    L21 は L16 の横断版であり、本プロトコル自身の L8 が検証対象の宣言を**要求**している。
    フィールドが無ければ発火せず、誤検知も原理的に起こらない。`requires` を実際に使う
    コーパスでノイズが出たら再検討する。

15. **SARIF 出力を手書きで持つ** — ジョブログの指摘は、レビュアーが該当ファイルを自分で
    探しに行くことになる。SARIF なら該当行に出る。GitHub が実際に消費する部分集合は
    素の構造体で書ける程度に小さく、ここで依存を足すのはこのバイナリ自身の供給網規律に
    反する。`diff --format sarif` は **added の指摘だけ**を載せる。継承コーパスの全量を
    アップロードすると毎回の PR に積み残しが注記されるからで、delta モードを作った理由と
    同じ。ツールメタデータに規則ごとの説明は載せない —— DESIGN.md の規則表の複製になり、
    ずれた複製は無いものより悪い。

16. **発火競合は引用句だけで判定する（L23）** — 規約は「発火が出ない・遅れる・一斉に出る」
    を規模の欠陥として挙げているのに、**スキル間**の競合を見る規則が無かった。description
    全体の類似度は却下した。誰も擁護できない閾値が必要になり、それを正直に決めるための
    実測が存在しないため。引用句は「ユーザーがこう言う」と作者が明示的に書き下したもので、
    2人の作者が同じ言葉を書いたなら、それは語彙の偶然ではなく同一リクエストの取り合い。
    154スキルの実コーパスで初版は14件発火し、うち2種類がノイズだった —— `"analyze"`
    （ルーン数の下限では語とリクエストを分けられない。4ルーンは英語では1単語、日本語では
    断片）と `"use ${CLAUDE_PLUGIN_ROOT}"`（実装者への指示であってユーザーの発話ではない）。
    語が空白で区切られる言語では空白を必須にし、`${` を含む句を除くと **8件・5スキルに
    なり、すべて実際の競合**だった（「how do I set this up」を3つのチャネルスキルが
    同時に主張している例を含む）。

17. **フローグラフの「読まれない側」（L24）** — L17 は「生成前に読む input」を捕まえたが、
    その逆である「誰も消費しない output」は Atlas の artifact ledger に出るだけで指摘に
    なっていなかった。L21 と同じく実測なしでの採用になる。測定に使えたコーパスには
    `flow.json` が1件も存在せず、L15・L16・L17 も含めて fixture に依存している。
    フローを宣言していないコーパスでは発火しようがなく、それが採用コストを安くしている。

18. **Tier 3 は記録された eval 結果を読む（実行はしない・L25）** — Tier は eval 2形式の
    **存在**を検証扱いにしていたが、それは「全ケース落ちているスキル」でも満たせる。
    eval の実行は `skill-creator` への委譲のまま（判断4）で、mekiki は
    `evals/results.json` を読むだけ。境界は動かさず runner も作らない。不在は無言なので
    既存資産に影響せず、発火精度は記録するが合否は判定しない —— 合格ラインには閾値が
    必要で、それを正直に決められる実測がここには無い。

19. **ランタイムプロファイル（既定は挙動不変・Phase 7）** — L2 が測る1,536字の一覧上限も、
    L12 の許容キーに含まれる拡張キーも、Agent Skills 標準の規則ではなく Claude Code の
    挙動である。コードに固定したままだと、標準のみを実装するランタイム向けに書かれた資産を
    静かに誤診する（そこでは `when_to_use` は本当に非標準キーであり、description に連結
    されもしない）。`profile` がこの2つを切り替え、`limits` が個別の閾値を上書きする。
    本文サイズの上限はランタイム固有では**なく**公式ガイダンス由来なので、どちらの
    プロファイルでも同じ値にした。受け入れ基準は「config 無し」と「`profile: claude-code`」
    の両方で154スキルのコーパスに対する出力がバイト単位で一致すること。この検証が無ければ、
    このリファクタリングは静かな挙動変更と区別がつかない。

20. **mekiki は Agent Skill（`skills/auditing-skill-corpus/`）を同梱する。許される理由は
    ラダーにある** — 規約は「新設は最後の
    手段」と言っているので、このスキルも作者の裁量で素通しにするのではなく、自分たちのラダーを
    通す必要があった。実際に通る。encode しているのは手順であって事実ではない（＝エージェント
    指示の1行では足りない）、設定で表現できる範囲を超えている、育てるべき既存スキルも無い。
    書く価値を生んだのは、mekiki の指摘文それ自体は読めば分かるのに**作業の順序**は分からない
    という非対称性で、エージェントが失敗するのは順序のほうである（継承資産にいきなり lint して
    編集を始める、warn を作業リストにする、散文ヒューリスティックを「文を消して」直す、ガードが
    未設定なのに名前を捏造する）。修復手順を `references/` に置いたのは層テストのためと、機械的な
    理由のため —— L8・L20 が検出するリスク語彙を引用せざるを得ないのに、この2規則が読むのは
    description と本文だけなので、本文に置くと説明対象の規則を自分で踏む。同梱スキルが無指摘で
    あることをテストが検査しており、これは規則そのものへの常設の検問にもなっている。

21. **初回接触用の2つ目の同梱スキル（`getting-started-with-mekiki`）** — これもラダーを
    通した。決め手になった問いは「なぜ `auditing-skill-corpus` を育てる形にしないのか」。
    2つの場面は Contract を逆方向に引っ張るからである。初回接触はコーパスの選択以外を
    すべて自分でやるべきで（インストール・実行・要約 —— 初心者に baseline の判断を訊くのは
    ノイズ）、監査は運用判断のたびに**止まる**べき（baseline、ガード名、重複が意図的か）。
    1つのスキルで両方に応えると、初心者に訊きすぎるか運用者の代わりに決めすぎるかのどちらかに
    なり、description は2つのトリガー語彙を同時に抱えて長さ上限を超え、規約が警告する
    過剰発火そのものに向かう。分割は機械的に取り締まる: 引用トリガー句は互いに素（`skills/`
    を lint するたびに L23 が検査）、双方の description と Non-goals に相互誘導、そして
    各スキルの eval の非発火クエリはもう一方を狙う。

22. **配布: 自己更新する tap と marketplace マニフェスト。リリースツールは使わない** —
    判断11は配布を採用障壁と名指ししたが、`go install` は依然 Go ツールチェインを前提に
    する。Homebrew formula は別リポジトリの tap に置き、タグの tarball からソースビルド
    する。この tap は**自分自身を定期更新する** —— 最新リリースを cron で確認して formula を
    書き換える方式なら、リポジトリは既定トークンで自分に push できる。通例の構成（リリース
    ワークフローが tap に push する）はリポジトリ横断の PAT を要求し、それはこのプロジェクト
    が持ちたくない常設クレデンシャルである。リリースバイナリを手書きワークフローでビルド
    するのは SARIF writer を手書きした理由と同じ —— 仕事の実体は `go build` のループであり、
    リリースツールはこのバイナリ唯一の依存になってしまう。`.claude-plugin/` のマニフェスト
    によりリポジトリは plugin marketplace を兼ね、同梱スキルは `cp -r` ではなく管理された
    プラグインとして入る。

23. **散文ヒューリスティックは識別子を無視する** — インラインコード・リンク先・引用符・
    ファイルパスを除いてから判定する。バックティック内のスキル名やファイル名は「名前を挙げている」
    だけで作業の記述ではなく、実コーパスに残っていた L6 誤検知はすべてこれだった。

24. **「この PR を lint して」は `mekiki pr` ではなく `lint` のフラグにした（`--changed`）** —
    資産全体の答えは `diff` としてすでにあり、そこに誤った問いが流れ込み続けていた。`diff` が
    比べるのは指摘の集合なので、指摘の顔ぶれを変えずにスキルを編集した PR は、触ったスキルが
    error だらけでも `no change` になる。欠けていたのは「触ったスキルの現状」という答えで、
    これは `lint` の絞り込みであって新しい動詞ではない。サブコマンドにすると `--format` /
    `--severity` / `--config` / `--baseline` を再び露出させることになり、しかも `pr` は嘘に
    なる — 入力は PR 番号ではなく git のリビジョンだから。既定の base を `origin/HEAD` に
    したので普段は引数不要で、専用動詞に期待していた直感性は実際にはここから来る。将来
    GitHub 連携（PR 番号の解決、コメント投稿）まで踏み込むなら、そのとき動詞が名前に見合う。

25. **絞るのは報告だけで、評価は絞らない** — 横断規則（参照の重複、存在しないスキルを指す
    フロー、同じトリガーの取り合い）こそ PR で効く規則なのに、どれも変更ファイルだけからは
    何も言えない。だから資産全体を探索して全規則を評価し、出力だけを絞る。指摘が残るのは
    触ったスキルのものか、**メッセージが触ったスキルを名指ししている**場合で、これにより
    削除が壊したフローが、その変更が開いてすらいないスキルで見える状態に保たれる。
    `--severity` と違い、この絞り込みは exit code も動かす。severity での絞り込みが赤い
    ビルドを緑にするのは故障だが、持ち込んでも触ってもいない error で PR が落ちることこそ、
    この仕組みが取り除く故障だから。

26. **判定規則は `lint` の opt-in フラグで、独立パッケージに置き、exit code に触れない
    （`--jev`）** — SKILL_PROTOCOL が *unenforced (review)* とする規約は、スキルが自分に
    ついて述べた主張を別の箇所と突き合わせる問いで、較正された分類器が計測上得意で正規表現
    には無理な唯一の領域に当たる。だがネットワーク呼び出し・鍵・非決定的な答えは、この
    ツールの制約 3 つに同時に反する。だから 1 つのフラグの裏、`internal/lint` が決して
    import しない `internal/jev` に閉じ、フラグなしではソケットを開かない。J の指摘は warn、
    `diff` は読み飛ばし（しきい値付近の判定は実行間でゆれ、add と resolve の往復に見える）、
    `--dry-run` は鍵なしで価格を出すので、送る前に何が送られるかが見える。名前はベンダー名
    にした。API の形は Jev 固有で、中立な `--judge` はそれを読み手から隠していた。ベンダー
    中立の動詞は 2 つ目のプロバイダが現れたときに名前に見合う。`mekiki pr` と同じ順序。

27. **Jev は追加と注記だけをし、抑制はしない** — J1 は判定した L6 の指摘を隠さず確率を
    添え、J4 は語彙の広さで実装できなかった L20 の層を warn として開き、どの規則も L8 を
    参照しない。安全規則は recall 優先（決定 12）で、モデルは state 内の敵対的な文を敵対的
    と扱わないが、正規表現は言いくるめられない。しきい値は暫定 0.5 で出荷する。
    `internal/jev/testdata/` の fixtures に対し鍵を持つ人が live 実行で fit を記録し、CI は
    鍵なしで replay する。fixtures は合成なので、実コーパスのものはリポジトリに入らない。

## 採用しなかったもの（理由つき）

- **公式バリデータ `skills-ref` への検証委譲** — "not meant to be used in production" と
  明記されているため撤回。必要な公式制約は mekiki 側に実装
- **`name` の64字上限・連続ハイフン等の追加検査** — 実コーパスで違反0件。
  1件も捕まえない規則はコンテキストと保守コストしか生まない
- **OpenAPI による完全な仕様記述・マスタの SQLite 化・既存スキルの一括改修** — 重い仕様書は
  守られない文書になる／破綻してから移行すればよい／段階適用で置き換える
- **ミニマリズムの強度モード（lite/full/ultra）** — 規約に強度スイッチを入れると SSOT が壊れる
- **描画プレビュー機構・更新通知機構** — スコープ外
